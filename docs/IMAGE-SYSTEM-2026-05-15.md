# Image / Logo System — actual setup (2026-05-15)

This doc exists because the "image hosting bill" assumption keeps recurring in planning discussions. **The current setup costs zero per month.** Every entity logo on every page resolves through one of three free / public endpoints, plus a deterministic client-side fallback for anything that 404s or is missing.

If you're tempted to provision Vercel Blob, S3, Cloudflare R2, or a CDN bucket for "logo hosting" — read this first.

**No Vercel Blob. No S3. No Cloudflare R2. No CDN bucket. No image-CDN bill. No image-CDN budget.**

## Why this works

### The three free endpoints are stable

- **GitHub avatars** at `github.com/<owner>.png` have been a documented public URL since at least 2012. No rate limit on the static avatar endpoint. Sized via `?size=N` (16-460 px).
- **Google favicons** at `google.com/s2/favicons` is a free public service Google has hosted for years. We use it after Clearbit retired their free favicon API in 2023.
- **HuggingFace** publishes author/org avatars via the public `/api/users/<author>/overview` and `/api/organizations/<author>/overview` endpoints. We dehydrate the URLs at commit time into `data/_meta/huggingface-avatars.json` via [`scripts/enrich-hf-avatars.mjs`](../scripts/enrich-hf-avatars.mjs) — this means the runtime is a synchronous object lookup with zero HTTP traffic during page render.

### EntityLogo handles every failure mode in-band

[`src/components/ui/EntityLogo.tsx`](../src/components/ui/EntityLogo.tsx) is the single primitive every surface uses for entity avatars. It:

1. Renders `<img loading="lazy" decoding="async" referrerPolicy="no-referrer">` when `src` is non-null.
2. Listens for `onError` and atomically swaps to the monogram tile if the upstream 404s.
3. Initialises with `errored = false` and `showImage = !!src && !errored` so a null URL takes the monogram path synchronously on first paint — no flash of empty space.
4. Picks a deterministic palette hue from the entity name (8 colors in `MONOGRAM_PALETTE` at [`src/lib/logos.ts:345`](../src/lib/logos.ts)) and a single uppercase letter (strip `r/`, `@`, `/` prefixes via `monogramInitial`).

This means **no upstream image source is load-bearing**. If GitHub avatars go down, every repo card falls back to a colored monogram. If the Google favicon service drops, every company logo does the same. The site degrades gracefully into a colorful initials grid, which is still readable and doesn't shift layout.

### The HuggingFace JSON is regenerated, not held

`data/_meta/huggingface-avatars.json` is regenerated by [`scripts/enrich-hf-avatars.mjs`](../scripts/enrich-hf-avatars.mjs) on a cadence (manual or CI-driven; not yet on a scheduled workflow). It scrapes the public HF API for ~2k known authors and writes the resulting URL map. That JSON is then bundled into the Next.js server build via a static import in `lib/logos.ts:15`. No runtime fetch from HuggingFace; the URL map is in the bundle and looked up synchronously.

If a HuggingFace author isn't in the JSON, the resolver falls through to the curated `HF_AUTHOR_DOMAIN_MAP` (lines 86-172 of `lib/logos.ts` — ~80 hand-curated big-tech / AI-lab mappings) → Google favicon. If neither applies, the HuggingFace platform mark renders. If even *that* fails to load, EntityLogo's `onError` lands on the monogram.

## What this costs

- **Storage**: nothing. We don't store any image binaries; we only store URLs.
- **Bandwidth**: nothing on our end. The user's browser fetches the image direct from GitHub / Google / HuggingFace. We add a `referrerPolicy="no-referrer"` so the upstream doesn't see referrer leaks but still serves the image.
- **CDN**: nothing. We don't proxy.
- **Cache**: nothing custom. We rely on browser cache + upstream cache headers.

## When you *should* host images yourself

If any of these become true, revisit:

- **The product needs editorial OG cards** with custom artwork per repo. (Currently we use Next.js `ImageResponse` to generate OG cards at request time — those are dynamic SSR responses, not hosted images.)
- **A user-uploaded asset surface** is added (e.g. profile photo upload). Then Vercel Blob private buckets become the right pattern.
- **GitHub or HuggingFace tighten the public-avatar endpoint** (e.g. require auth, rate-limit) — historically unlikely but always possible.
- **Measured demand** for a logo through-pool that the TOOLBOX worker can de-rate (the `worker` package referenced in CLAUDE.md does run image fetches for some flows — consult that doc for the worker-side image-cache design if/when it gets exercised).

Until then, the system is correct as it stands.

## Per-surface trace (where do logos render?)

The single primitive is `<EntityLogo>`. As of 2026-05-15 it has 30+ call sites — every feed, every card, every leaderboard, every sidebar. New surfaces should consume it directly. To audit:

```bash
git grep "EntityLogo" -- "src/"
```

If you're adding a new entity that needs a logo, write a helper alongside the existing ones in `src/lib/logos.ts` (`<source>LogoUrl(...)`) and feed both the URL and the entity name into `<EntityLogo src={url} name={entity} />`. The monogram fallback is automatic.

## Open items (intentionally deferred)

- **`scripts/enrich-hf-avatars.mjs` is not scheduled**. New HuggingFace authors that appear after the last manual run will land on the corporate-domain map or the HF mark, not their real avatar. Add a daily workflow if avatar drift becomes visible.
- **No server-side monogram endpoint**. The plan considered `src/app/api/logo/[seed]/route.tsx` returning an `ImageResponse` monogram for external consumers (OG cards, embeds). Skipped because every in-page use already gets a client-side monogram via EntityLogo. Revisit only if an external consumer (e.g. share-card builder, email render) needs the monogram as a real PNG URL.
