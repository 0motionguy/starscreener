## What IS wired

- The **worker** (`apps/trendingrepo-worker`) writes to Supabase tables
  `trending_items`, `trending_metrics`, `trending_assets` via
  `apps/trendingrepo-worker/src/lib/db.ts` (`upsertItem`, `writeMetric`,
  `upsertAsset`, `queryTopByType`). Schema lives in
  `apps/trendingrepo-worker/supabase/migrations/` (5 migrations, latest
  `20260504000000_trending_items_updated_at_source_only.sql`).
- The **main app** reads exclusively from Redis via `src/lib/data-store.ts`
  with bundled JSON + in-memory fallback. Collectors dual-write file +
  Redis through `scripts/_data-store-write.mjs`. No Supabase write or read.
- The **trending_items** table the worker uses is a different schema entirely
  from the proposed `cron_payloads` lake (per-source columnar projection vs.
  one-table-with-JSONB append-only lake). Reusing it for Phase 1a is not
  drop-in; it would require either a new table or a schema rethink.

## Recommendation

**(b) Update ADR 0001 status to "Deferred" - worker-only Supabase path is
sufficient for current scale. Effort: ~30 min ADR amendment.**

Rationale:

1. **No present pain.** The replay / time-series / analytics use cases the
   ADR justifies (sections "Context" and "Consequences > Positive") are all
   speculative. We have not had a "bad scan poisoned history" incident the
   lake would have rescued; the current rate-limit + dedupe in the refresh
   hooks plus Redis hot cache has been stable since the 2026-04-26 collector
   shift to direct mode.
2. **Cost asymmetry.** Phase 1a alone is ~1 day (add dep, write
   `supabase-store.ts`, extend `_data-store-write.mjs` to triple-write,
   provision env in GH Actions + Vercel + worker, smoke test). Phases 1b
   + 1c double that. Versus a 30-minute ADR amendment that records the
   decision and unblocks the DATABASE.md rewrite.
3. **Worker already covers the analytics use case** for the highest-value
   shape: `trending_items` + `trending_metrics` give us per-source
   time-series for the leaderboard surfaces, which is the analytics ask
   that has actually shown up in product conversations.
4. **Append-only invariant is preserved by RLS** in the schema even if we
   later turn it on - the migration is forward-compatible. Deferring is
   reversible at near-zero migration cost.

When to revisit (a): if we (i) ship the `/api/history/<source>` route the
ADR sketches (Phase 2 in the ADR), (ii) hit a real bad-scan incident that
needed a prior good payload, or (iii) need cross-source replay for an
audit. None of those are on the current sprint.

The amendment text suggested for the ADR (when (b) is taken): change
`Status: Proposed` to `Status: Deferred 2026-05-05 - worker-only Supabase
path covers current scale; main-app dual-write parked until a concrete
replay/history requirement materialises. See docs/archive/ADR-0001-status-2026-05-05.md`.
